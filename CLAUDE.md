# BlokDunyasi - Global Project Contract

This file is the top-level operating contract for AI/code agents working in this Unity project.
Read it before touching files. If a more specific instruction exists in an active sprint file, the sprint file wins for that sprint only.

## Project Identity

- Product: Blok Dunyasi
- Studio: Krayirhan Studio
- Engine: Unity
- Main platform: Android
- Project root: `I:\Unity_Projeler\BlokDunyasi\BlokDunyasi`
- Do not treat the outer `I:\Unity_Projeler\BlokDunyasi` folder as the Unity project root.

## Workspace Rules

- Assume the worktree can be dirty.
- Do not revert user changes unless the user explicitly asks.
- Do not run destructive git commands such as reset, checkout, clean, or forced deletion.
- Do not commit unless the user explicitly asks for a commit.
- Before large edits, inspect current file state and nearby code.
- Prefer small, verifiable changes over broad rewrites.
- If a file is generated by Unity, avoid manual edits unless the task requires scene or asset serialization changes.

## Architecture Boundaries

```text
Assets/Scripts/Core/          pure C# domain logic
Assets/Scripts/UnityAdapter/  Unity-facing adapters and MonoBehaviours
Assets/Scripts/UI/            legacy/app-level UI and ads helpers
Assets/Scripts/Systems/       startup and app services
Assets/Scripts/Editor/        Unity editor tooling
Assets/Scenes/                Unity scenes
Tests/BlockPuzzle.Core.Tests/ standalone core tests
```

Dependency direction:

```text
UnityAdapter -> Core
Core -> UnityEngine is forbidden
```

Core rules:

- `Assets/Scripts/Core/**` must not reference `UnityEngine`.
- Core logic must stay deterministic where practical.
- UI, ads, Firebase, PlayerPrefs, scenes, MonoBehaviour lifecycle and Unity objects stay outside Core.

## Current Hotspots

Treat these files as high-risk:

| File | Risk |
|---|---|
| `Assets/Scripts/UnityAdapter/UI/GameOverView.cs` | Godfile, final screen, continue/rewarded flow, scene navigation |
| `Assets/Scripts/UnityAdapter/Boot/GameBootstrap.cs` | God object, gameplay orchestration |

| `Assets/Scripts/UnityAdapter/Blocks/NewBlockTray.cs` | Input/layout/gameplay coupling |
| `Assets/Scripts/UnityAdapter/UI/MainMenuController.cs` | Menu UI, scene navigation, layout coupling |
| `Assets/Scripts/UnityAdapter/UI/HighScoreTableView.cs` | Firebase leaderboard rendering |

Godfile policy:

- Do not add new responsibilities to a godfile unless this is the smallest safe fix.
- Prefer extracting pure helpers, presenters, state structs, or service seams.
- If a godfile must be changed, keep the diff local and add verification.

## Product Invariants

- Leaderboard data comes from Firebase only.
- Current user is displayed as `Sen` in Turkish UI.
- Public leaderboard collection is `leaderboard_public`.
- Firebase Console score override fields are `scoreOverride` and `weeklyScoreOverride`.
- Canvas reference resolution is `1080 x 1920` with match `0.5`.
- Build scenes are `MainMenu`, `OyunEkranı`, and `Scores`; do not assume a dedicated `GameOver` scene exists.

## Verification Commands

Use the smallest relevant verification set. For broad changes, run all:

```powershell
dotnet build Assembly-CSharp.csproj -v:minimal
dotnet build BlockPuzzleUnityAdapter.csproj -v:minimal
dotnet test Tests\BlockPuzzle.Core.Tests\BlockPuzzle.Core.Tests.csproj -v:minimal
git diff --check
```

Notes:

- `BlockPuzzleTests.csproj` is Unity-generated and may not list actual Unity PlayMode tests from CLI.
- Unity scene behavior still requires Unity Editor or device/play mode validation.
- If a verification step cannot run, report why.

## Sprint System

Sprint source of truth:

```text
sprints/
  _rules.md
  _template.md
  backlog.md
  active/
    sprint-XX/
      brief.md
      tasks.md
      report.md
  archive/
```

Rules:

- At most one active sprint folder exists under `sprints/active/`.
- Sprint work must map to a task in `tasks.md`.
- New scope discovered during implementation goes to `backlog.md` unless the user explicitly expands the sprint.
- `report.md` is filled only when closing the sprint.

## Definition Of Done

A task is done only when:

- The requested behavior is implemented.
- The smallest relevant verification passes.
- No known P0/P1 regression is left unreported.
- Any unfinished or newly discovered work is added to `sprints/backlog.md`.
- The final response includes what changed and what was verified.
